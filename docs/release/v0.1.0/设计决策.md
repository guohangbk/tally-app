## 1. 总原则

| 原则 | 含义 | 反面例子 |
|---|---|---|
| 机器猜的必须人点，人定的直接入账 | 语音、截图、AI 是**机器在猜**，只出草稿，人按「记入」才落库；周期与分期是**人预先做好的决定**，到期直接入账——决定在做计划那一刻就做过了 | 「自动入账」开关被永久移除，而不是默认关；一次要补的期数超过 100 才停下来等确认 |
| 单一事实来源 | 同一个数字、同一个标记，全站只有一处定义 | 统计页与首页各算各的合计，对不上 |
| 入口不重复 | 一件事只有一个入口，出现两次就是设计失误 | 底部 tab 与 ＋ 都能进小莉，砍掉一处 |
| 少一层跳转 | 能在当前页完成的不到新页，能弹窗的不推入页 | 账单详情页 → 底部卡片 |
| 状态可见但不喧哗 | 选中、禁用、排除都要看得见，但不靠颜色单独表达，也不常驻提示 | 蓝色高亮选中、顶部横幅 |
| 本地优先 | 断网能用是底线，AI 只是锦上添花 | 未配置的 AI 入口直接不显示 |
| **能兑现才承诺** | 系统能力（通知、组件、快捷方式）在厂商 ROM 前不可控，界面只承诺验证过的部分 | 「每天 20:00 准时提醒」改成「今天之内提醒」；组件不做写库按钮 |
| **口径先于界面** | 任何新数字先进口径表再上界面，页面只引用不自己算 | 退款冲抵、月起止日、预算三个数字都先定义再画屏 |
| **找回走页面，不走气泡** | 反悔窗口是短暂确认，找回是正式功能，两者不互相顶替 | 回收站是页面，删除气泡不挂「撤销」 |

## 2. 导航：为什么没有底部导航

**问题**：照惯例做过底部四格导航（账单 / 统计 / 小莉 / 设置）。实际自用发现：记账是 90% 的动作，其余都是低频查看，底栏把最贵的屏幕底部让给了低频项；而且「小莉」既是 tab 又出现在别处，语义分裂。

**结论**：**撤掉底部导航**。首页成为唯一常驻页；统计与搜索放顶栏右侧；管理入口收进左侧抽屉；记一笔与三个智能入口全部挂在 **＋** 上（短按记账、长按出三臂：上语音、左截图、右小莉）。

**代价**：统计少了一个常驻位，靠顶部图标进入；用户需要一次学习「长按 ＋」。

**被否决**：① 底栏保留两格（账单 / 小莉）——两格不是导航，是占位；② 给小莉单独 tab——它只是对话页，不是并列的一层；③ 三臂改成侧边滑动——单手够不到，且与系统返回手势冲突。

## 3. 记一笔：再记为什么和保存同权重

**问题**：连记 8 笔要重复 8 次完整流程（选分类、输金额、保存、回列表、再进记账）。

**结论**：保存与**再记**做成两个等高同宽的键。再记保留分类 / 类型 / 标记 / 日期，只清金额、备注、图片，并停在原地显示会话计数。第二笔起 ≤ 2 步。

**代价**：键盘最后一行被两个动作占掉两格，数字区少了位置——所以键盘改成 4×4 十六格而不是 3 列。

**被否决**：① 保存后弹「是否再记一笔」——多一次打断；② 把再记做成小字次要按钮——被读成不重要的动作，几乎没人用。

## 4. 键盘：为什么是 4×4 而不是 3 列 + 右侧竖排

**问题**：3 列数字 + 右侧竖排双键（⌫ / ＋）时，键高被压到 35dp，拇指误触且「−」「＋」不在同一节奏里。

**结论**：4×4 十六格等宽等高（42dp）：`123⌫ / 456− / 789＋ / 再记 0 . 保存`。**没有等号键**——保存就是等号；`+/−` 进入算式态。

**代价**：编辑态需要另一个动作位，于是把左下的「再记」换成「放弃」（仅在改动后拦一道）。

**被否决**：① 加等号键——多一次点击，且等号后的结果还是要靠保存落库，语义重复；② 保留独立语音键——与长按 ＋ 重复。

## 5. 账单详情：为什么是弹窗且不能就地编辑

**问题**：详情页 + 就地编辑意味着两套编辑 UI、两套校验、两套状态同步，实测改一笔要在一屏里点三次。

**结论**：点账单行弹**底部卡片**，只读展示全字段 + 动作行；「修改」跳记账页并带原数据。全站只有一处记账表单。

**代价**：改一个字段也要进一次记账页，看起来多了一步，但换来零重复实现与零状态不一致。

**被否决**：① 详情页内联编辑——第二套表单，长期是 bug 源；② 卡片里放分类选择器——把记账表单抄了一遍。

## 6. 批量操作：为什么是长按而不是勾选框常驻

**问题**：每行一个勾选框会永久吃掉左侧 32dp，且暗示「这里可以选」，与浏览场景冲突。

**结论**：**长按进入选择态**，行首才出现勾选框，底部顶起动作条；返回优先取消勾选而不是退出页面。

**代价**：批量入口不可见，靠首次引导与文档传达。

**被否决**：① 右上角「批量」开关——多一次点击且状态不连续；② 复选框常驻——浏览时全是噪音。

## 7. 分类：为什么是全机一套字典而不是每本一棵树

**问题**：按账本隔离分类树的结果是——新建账本要重配一遍分类，同一类「三餐」在多本里是不同 id，统计与 AI 分类表都要按账本拼，导入还要处理跨本同名分类。

**结论**：分类是**全机字典**，账本只是账单的容器。新建账本直接复用同一棵树；「上次分类」是一对全机键；AI 的分类表每轮现算一次全局短柄 `c01…cNN`；`keyword_rule` 同样不带 `ledger_id`。

**代价**：① 需要一次性合并历史上各本重复的默认树（同 `(层级, 父级, 类型, 名称)` 只留一个节点，内置 `seed-` 前缀的 id 字典序在前，所以留下的总是内置那份），四个表的引用改指留下的节点；② 删除分类的影响面变成跨账本，提示文案与迁移逻辑都按「全部账本」口径。

**被否决**：① 账本各自一棵树 + 复制模板——用户要维护 N 棵树；② 分类挂多账本的关联表——查询与迁移复杂度陡增，收益只是「看起来更灵活」。

## 8. 分类界面：为什么密集平铺而不是缩进树

**问题**：缩进树在 6 英寸屏上一屏只能看 4 个一级，展开二级要跳页或长滑。

**结论**：一级是一张卡片，二级收进卡片内 **5 列平铺纸盘**，不缩进、不开新页；同屏可见 7 个一级。操作走 **⋯ 动作弹层**，弹层里只列动作不放输入框；「修改」打开预填好的全屏页。

**代价**：卡片高度固定，二级很多时需要展开滚动。

**被否决**：① 缩进树——层级视觉噪音大；② 弹层里就地改名——键盘一弹，弹层高度就崩，且与全屏修改页重复。

## 9. 标记体系：为什么必须单一事实来源

**问题**：报销、不计入收支、周期、分期、导入、小莉这些标记如果在记账页、卡片、批量三处各自画各自，文案与颜色不一致，用户搞不清「已报销算不算支出」。

**结论**：一套 `Marker` / `BillBadges` 组件 + 一张口径表：报销只作用于支出；不计入收支只影响金额汇总，不影响列表与笔数；**已报销那几笔不再计入支出合计**（待报销照常计入），金额单列在 `BillSummary.reimbursedMinor / reimbursedCount` 里对账；金色只留给机器产出的账。统计、导出、搜索合计引用同一份实现。

**代价**：任何新标记都要先进口径表才能上界面，加字段变重了。

**被否决**：① 通用标签系统——归堆这件事账本已经承担得更好，标签只当切片会影响不到口径，却要多两张表、一个管理页、一套绑定关系；② 每处自己写文案——就是当初出问题的原因。

## 10. 统计：为什么一页四段 + 点按才算

**问题**：统计页一进来就发 AI 请求，既慢又贵；页面又拆成多个子页，看一次「哪类涨得最快」要点三次。

**结论**：一页四段（总览 / 分类 / 排行 / 趋势）共用**一次查询快照**，换维度只重算数字不跳页；AI 分析改成**右下角一颗胶囊，点了才算**，结果按月份 + 输入摘要哈希缓存，数据没变直接复用。

**代价**：AI 分析不是「打开就有」，需要用户主动一次。

**被否决**：① 每日定时自动分析——耗电、耗 token、结果没人看；② 首页常驻 AI 卡片——把增强能力变成了视觉主角。

## 11. 小莉：为什么卡片要落库

**问题**：记账卡存在 ViewModel 的 map 里，进程被系统回收后卡片消失，用户以为「它答应了又忘了」。

**结论**：卡片作为 `ai_message` 的 **DRAFT 行**落库，「已记入 / 先不记」状态也写在行上；「先不记」是划掉保留而不是删除气泡。

**代价**：多了两张表与一套状态字段；删除对话时要连带处理。

**被否决**：① 只存内存——不可靠；② 「不要」直接删消息——用户会怀疑自己那句话也没了。

## 12. 小莉配置：为什么删掉状态灯、把能力改成勾选

**问题**：配置页有状态点，卡片里写「已就绪 / 在线 / 疑似异常 / 已断开」；同时模型是否支持图片靠自动探测，探测不准时用户只能手动覆盖，界面越补越多。

**结论**：

- 界面**不显示任何连接状态标签**：异常由那次调用当场说明，常驻灯没人看得懂。
- 服务商与模型改成**下拉预置**（OpenAI / DeepSeek / 智谱 / 千问 / 自定义），选完自动带出地址与常用模型；base URL 仍可改成中转。
- 图片能力改成**保存前的一次勾选**，并直接决定对话页能否发图；删掉自动探测代码，避免「探测说支持、实际不支持」和「说不支持、其实能用」两头挨打。
- **保存成功后收起表单只留一张配置卡**，要改点「修改」——只维护一个当前模型，不需要表单常驻。

**代价**：用户勾了图片但模型实际不支持时，发图会失败（错误照实回显）。

**被否决**：① 保留自动探测 + 手动覆盖双轨——两个真相；② 支持多模型库与按任务路由——只有一个当前模型，没有路由需求。

## 13. 提示与反馈：为什么是贴底气泡

**问题**：顶部横幅会挡住刚点开的弹窗内容；同一句错误在页面上方和弹窗里各出现一次。

**结论**：一次性反馈统一走**贴底自动收起的 `TallyToast`**；只有弹窗内容态、卡片内错误态、引导页阻塞态才用卡内提示；页上有弹窗时，页面级气泡不得接手同一条错误。每屏最多一条灰字说明，解释性文字一律进文档不进界面。

**代价**：提示转瞬即逝，重要错误必须同时落在控件状态上（禁用 + 原因）。

## 14. 震动与图标：为什么统一收口

- **震动**：一个 `TallyHaptics` 收口，按语义分 tap / key / longPress / confirm / reject，全部走系统反馈常量，跟随系统触感开关，不需要额外权限。散在各页自己 `performHapticFeedback` 会让手感不一致。
- **图标**：只存 `icon_key`，图形来自内置 136 个分类图标 / 12 组，二级各自独立不继承一级。存图片路径会带来备份体积与失效引用问题。

## 15. 数据与升级：为什么是逐级手写迁移

**问题**：单机自用软件频繁改实体。要么每个版本手写迁移（每次迭代都要付一次成本），要么清表重建（升级即丢数据，只能靠备份包搬）。

**结论**：**`version = 1` 起步，手上没有已发布过的旧版本，就不写迁移文件**；此后每一次改实体都必须**手写 `Migration(n, n+1)`，且不配 `fallbackToDestructiveMigration`**。理由是清表重建给「忘记配迁移」留了一条**静默清库**的后路——它把工程失误转嫁成用户的数据损失。手写迁移出错同样危险，但错误会**报错停住**，停在用户可以自己救（用 `.tally` 备份恢复）的位置上。

同理，一串外部没人能升上来的旧迁移不是资产而是负债：它没法被任何人验证，却会让人误以为升级路径是可靠的。

配套三条硬规矩：① 改实体 = `version` +1 且补一段迁移，两件事一起做；② 每段迁移前后各跑一次行数比对写进 `DebugLog`，升级后能一眼看出哪一级跑过、搬了多少行；③ 每次实体改动重跑 KSP 导出 `N.json` 入库，手写 SQL 与实体声明不一致时 Room 打开即报 schema 校验失败。

**被否决**：① `@AutoMigration`——改名 + 值映射 + 去重合并三件事它做不了，且不生成可读 SQL，出问题无法复盘；② 静默保留旧列——schema 会长期带着已废弃字段；③ 为无变化的批次空转版本号。

## 16. 提醒：四类通知，不是一个消息中心

**问题**：自动补执行如果完全静默（`Result.retry()` 之后没人知道），用户就永远不知道自己错过什么；最容易的补救是做一个「消息中心 / 通知历史」列表页。

**结论**：只做四类可独立开关的通知——当日未记账、周期到期、分期到期、执行失败（外加一类系统：回收清理）。**不做应用内消息中心**。设置页只回答两件事：开不开、几点开。

**代价**：用户错过通知就看不到历史（系统通知栏会自己留，不归 App 管）。

**被否决**：① 应用内消息中心——没有需要沉淀的通知内容，为了「看起来完整」建一张表和一个页；② 把所有提醒合并成一个开关——失败提醒和未记账提醒的打扰度完全不同，合并等于让用户一起放弃；③ 为四类提醒建一张提醒记录表——一个日期标记就够，多一张表就多一处迁移。

## 17. 「今天没记账」怎么判定

**问题**：这句话有三种口径：今天没有**支出**、今天没有任何账单、今天没有**新增**（编辑旧账不算）。

**结论**：**当天不存在 `deleted_at IS NULL` 的任意账单**才提醒，方向不限。当天只记了一笔收入也算「在记」。

**代价**：漏掉「只改了备注没记新账」这种情形——但那本来就不是习惯断裂。

**被否决**：① 只看支出——自由职业者当月只有收入的日子很多，会被误打扰；② 连续 N 天没记才提醒——第一次断裂就流失，等 N 天太晚；③ 按「本月已记笔数低于均值」这种统计口径——用户看不懂为什么被提醒。

## 18. 通知点达，不加应用内红点

**问题**：通知点进去要落到哪。另一条路是通知只负责「叫你打开 App」，进 App 后在抽屉上挂红点。

**结论**：通知自带路由——未记账提醒进记账页，到期提醒进对应规则并定位，失败提醒进周期页。抽屉与顶栏**不加红点**。

**代价**：用户不点通知就再无提示。

**被否决**：① 红点 + 通知双轨——同一件事两个压力源；② 通知只做跳转不带动作——「记一笔」直发深链，省一次开 App 找页面。

## 19. 回收站：找回从气泡搬到页面

**问题**：删除只靠软删 + 一条极长的撤销气泡兜命。8 秒是为了「万一删错」而把气泡撑得很长，代价是挡住别的提示，而且错过就再也找不回来——用户其实不知道数据还在库里。

**结论**：做回收站（按删除日期分组、可单条 / 整组 / 长按批量恢复、可彻底删除、保留期可设默认 30 天），**同时把撤销气泡整体下线**——删除气泡只报结果并写明「可在回收站找回」，不再挂「撤销」动作。

**代价**：多一个页面与一个清理任务；「彻底删除」要连带处理附件。

**被否决**：① 只做撤销不做回收站——用户看不见被删的数据在哪；② 撤销与回收站并存——长气泡本来就是被抱怨的对象，两套找回机制也让人不确定该用哪个；③ 回收站做在设置里当一段列表——恢复是高频动作，值得一个独立页；④ 新建一张回收表——读的就是每次删除都在写的 `deleted_at`，找回是查询与状态位问题，不是新数据。

顺带清掉了因此变成死码的 `BillRepository.snapshot/restore` 与 `BillDao.restore`：回收站走按 id 批量置空的那条更对的路径，不需要先取快照再整批 REPLACE 回去。

## 20. 附件回收按内容哈希，不按行

**问题**：做回收时最容易写成「软删账单 → 删它的文件」。

**结论**：文件按 **SHA-256 引用计数**回收——哈希去重从第一版就在做，同一张图片可能被多笔账单引用。只有零引用且超保留期才物理删；先删文件后软删行，任务可重跑。

**代价**：清理任务要多一次聚合查询；「引用」的定义要把软删账单也算进去（否则回收站里的账单图片会被删）。

**被否决**：① 按行删文件——直接毁掉另一笔共享同一图片的账单；② 不做回收只加存储提示——用户看到「占用 2GB」却没有任何出路。

## 21. 应用锁：为什么不做

**问题**：账本是最不该被看见的数据之一，但手机经常递出去。当时定了三件事——锁只在导航层判一处、生物识别优先且 PIN 一定可用、放开 `DEVICE_CREDENTIAL` 做忘记 PIN 的出路。

**后来整条不做。** 复核时指出：系统级应用锁（各家的「应用加锁 / 隐藏应用」）已经覆盖「把手机递出去」这个场景，App 再套一层只是多一道解锁摩擦，并且多一份 PIN 与生物识别的泄露面——而它防的其实和系统锁是同一件事。解锁页、锁设置页随之取消，`USE_BIOMETRIC` 权限不申请，全部权限增量只剩 `POST_NOTIFICATIONS`。

**留下的一条**：通知在锁屏预览态不带金额与分类名。它不依赖应用锁，任何时候都成立，由 `TallyNotifier` 的 `setPublicVersion` 实现。

**当时那条推理为什么值得留在这里**：「门禁判定只在导航层一处，页面不参与」对**任何**跨页面的门禁都成立——三十几个页面每页自己判必然漏。以后若真要加门禁（比如给某个账本单独加锁），别再走「每页判」这条已经被否掉的路。

## 22. 深链、组件、备份恢复的先后

**问题**：通知点达、组件点击、快捷方式都要回答「先落位还是先准备」。

**结论**：**intent 先存住，准备好之后继续跳转**。触发条件是「偏好读完、导航图就绪」——`TallyAppRoot` 在读到 DataStore 之前只画一张干净的纸面，避免闪一下引导页；通知点达沿用同一条路径：`MainActivity` 把 intent 交给一个应用级的待跳转状态，导航图就绪后消费掉。失败或取消则丢弃，不停在半路。

外部入口落到记账页时**先把栈收到首页再压一页**：`launchSingleTop` 会复用栈里那张旧页，路由换了而参数没换——组件上点「收入」还是上一次那笔支出。

恢复备份这条路径的规则是覆盖式、失败不动现有数据；**不做**「恢复后自动恢复某些设备本地配置」——那些配置不在备份包里，凭空恢复等于骗人。

## 23. 语音与截图去 AI 化：主动砍掉一条补救路径

**问题**：语音与截图在端侧规则之后，如果小莉开着，还会**再发一次请求把整份草稿覆盖掉**。真机反馈的「二十九块八毛五记成 29.8」有两半成因：规则层截断，和 AI 覆盖全字段。后者更隐蔽：**本地已经算对的金额被改写**。

**结论**：**语音与截图不叠加二次抽账**，只跑端侧规则。AI 在产品上收敛到两处——小莉对话页、统计页 AI 分析。不留开关，`needsAi` / `applyVerdict` 与记账链路上的 `enhance()` 调用整体删除（`enhance()` 本体保留，对话页在用）。

**代价（明确承认）**：规则层读不懂的表达（一句话混三笔、非标准说法）从此没有就地补救，用户得去对话页说一遍。这是主动取舍，不是缺陷。

**被否决**：① 保留但默认关——留着就有人会开，开了就有「它把我算对的金额改了」的反馈；② 只让 AI 补空字段不覆盖已填——听起来稳妥，实际要维护两套字段级冲突判定，而且模型对「29块8毛5」的理解本身不可靠；③ 加「本地优先 / AI 优先」设置——把设计矛盾转嫁给用户。

## 24. 关键词沉淀：「越用越准」的最小成立形态

**问题**：规则表读侧齐全、写侧为零，一行数据都没有。要补的不是一个「AI 训练」功能，而是两条路：能看能删的管理页，和一条零成本的沉淀入口。

**结论**：沉淀动作挂在**保存成功之后的一条气泡**上——机器预填的分类被你改成别的分类时，说一句「以后「打车」都记到 交通 · 打车」，按钮「确定」。管理页只做增删查与改绑，不做权重、不做统计、不显示「命中次数」。

目录是订阅出来的，所以刚沉淀、刚手加、刚改绑的词**当场生效，不用重启**。

**代价**：没有命中统计就无法回答「这条规则到底有没有用」；用户可以沉淀出一堆互相冲突的规则（靠「用户规则优先 + 内置词只读」压住）。

**被否决**：① 命中次数与「训练」面板——要新增写放大（每次命中都写库）和一个统计口径，收益只是数字好看；② 在规则页里做「试一试」输入框——与语音页重复；③ 自动沉淀（改了分类就默默写规则）——违反「机器不替人做决定」；④ 内置词组按名称兜底——只认种子 id，id 不存在（用户重建过分类树）就让整组失效并显示警示态，改名不再让一组词静默失效。

## 25. 时刻记账：精度是录入粒度，不是显示粒度

**问题**：`time_precision` 这个偏好若没人读，保存就永远硬编码 `DATE`。要定清这个开关到底管什么。

**结论**：**录入粒度**。开「时刻」＝记账页出现时刻选择器、保存写 `DATETIME`、首页按「日 + 时刻」分组排序；关＝保存把时刻归零到本地 00:00（避免同一天出现 0 点与 12 点两种键）。显示上不再单独设开关，也不进列表：**列表行尾只放备注**——一屏几十行铺满 `HH:mm` 既吵又难看，而且设置关着时历史 `DATETIME` 行仍冒时刻，看着像 bug。时刻属于这一笔的细节，点开弹层看，那里两行：账目时间（按该笔精度）与「记录于 `created_at`」。

**代价**：同一账本里混着两种精度的行，首页分组按真实时间排，00:00 落在一天最前，可接受。

**被否决**：① 只做显示开关——数据里根本没有时刻，显示什么；② 全局强制时刻——每天几十笔的人每次都要多点一下；③ 提供「批量补时刻」——绝大多数历史笔次不需要。

## 26. 桌面：两条快捷方式、三枚只读组件

**问题**：竞品长按图标常有五项（添加小部件 / 添加支出 / 添加收入 / 统计 / 搜索）。照抄会把「快捷方式」变成第二个主导航。

**结论**：只做两条——**记一笔**（收支合成一条，记账页本来就有 tab）与**添加小部件**（调系统钉件请求）。组件三枚（近七日、预算环、当日当月），全部**只读**，点击分区块落：数字区与柱条区进统计，＋ 钮进记账页，其余回首页。

组件走平台 `RemoteViews` 而不是 Glance：三枚组件全是文本 + 背景块，Compose 那套表达用不上，换来的是零新依赖与离线可构建。刷新由三个自己掌握的时机驱动（`onUpdate`、`MainActivity.onResume`、每日那次 Worker），`updatePeriodMillis = 0`——系统级轮询被 ROM 省电策略管着，不如自己按。桌面上没有实例时连库都不碰。

**代价**：想要「一键添加支出」的人多点一次；组件里不能直接记，少了一点爽感。

**被否决**：① 组件里内嵌数字键盘——把记账表单抄第二遍，违反「单一表单」；② 快捷方式带分类名（「记一杯咖啡」）——轻度隐私暴露在桌面图标上，且动态快捷方式的厂商行为不可控；③ 桌面做统计与搜索入口——顶栏已有，桌面重复；④ 组件里放写库按钮——同 ①。

## 27. 凭证图：为什么仍是一笔一张

**问题**：多图看起来是「更完整」。但要一起定的还有上限、顺序、封面、逐张删除、逐张压缩失败处理，以及 `sort_order` 列与一个多图条界面。

**结论**：**一笔一张**。凭证的作用是「这笔钱有张据」，一张足够回答这个问题；真要存多张收据，正确做法是记成几笔账单，因为它们本来就是几笔钱。查看器仍做成全屏组件并与小莉对话图片共用。

**代价**：一次买三样东西拍两张照片的人，第二张得手动再记一笔。

**被否决**：① 上限 9 张 + 可拖排序 + 首张为封面——这套界面成本换来的只是「看起来和竞品一样」，而且它把存储只增不减的风险（要靠引用计数回收才能压住）提前引入了；② 支持视频 / PDF 凭证——解码与预览成本完全是另一个量级；③ 「设为封面」单独动作——既然只有一张，不存在封面问题。

## 28. 图片查看器为什么破例做成全屏页

**问题**：定了「账单详情是底部弹窗，不做详情页」。图片查看器如果也做成弹窗，就要在弹窗里再弹一层；如果做成页面，又像是开了「详情页」的口子。

**结论**：查看器是**全屏页**，但它是**媒体容器不是账单页**：进去只有图、缩放、尺寸信息，不显示分类金额备注，也不提供编辑。账单详情弹窗仍只读 + 动作行。

**代价**：多一条路由与一条转场；「看图」和「看账」被拆成两跳。

**被否决**：① 弹窗内翻页——手势与下拉关闭冲突；② 在详情弹窗里直接展开大图——把弹窗变成详情页，正是当初否掉的东西；③ 对话页另做一套看图预览——两处生命周期不同（一个是临时文件，一个是库里的资产），只共用组件不共用状态。

## 29. 预算：按账本、只提醒、不做目标

**问题**：预算的形态很多：全机 / 按账本 / 按分类 / 按周 / 结转 / 储蓄目标。

**结论**：**按账本**（与账单归属一致，避免「三本共用一个预算」的解释成本）；总额 + 分类两档；周期月或年；**随月起止日滚动**；只发阈值通知，不在页面常驻红字（进度条转陶土即为表达）；进度用**净支出**（含退款冲抵），与统计页数字一致。一行属于一个具体周期段（`period_start`），可自动续期到下一段，往期只读回看。

**代价**：不能做「旅行预算只花三天」这种临时段（可以用统计的自定义区间看，不占预算位）；不做结转（结转会把「上个月没花完」变成需要解释的概念）。

**被否决**：① 全机一个预算——与账本模型打架；② 按周预算——自用场景里周预算的抖动太大；③ 存钱计划 / 目标金额——本质是迷你账户，与「不做资产体系」同源；④ 超支后禁用保存——预算是提示不是权限；⑤ 页面上常驻进度环 + 红色超支——违反「状态可见但不喧哗」；⑥ 给预算单独设唯一索引——软删行仍占唯一位，恢复时会撞，重复交给 Repository 写入前校验。

## 30. 退款：独立行 + 从原单分类冲抵

**问题**：电商退货本质是「一笔钱分几次退回来」。

**结论**：退款是**独立账单行** + `refund_of_bill_id` 指向原单，**从原单分类的支出中扣除，不计为收入**；允许多次，累计不得超原单。旧导入产生的退款行没有原单可指，界面如实显示「未关联原单」，统计上是中性行。

**代价**：统计页要能解释「为什么收入没有增加」；列表行上的「已退」金额是 `refund_of_bill_id` 的关联子查询，所以这一列必须单独有索引（无索引时每行全表扫描，一次取几百行就放大成秒级卡顿）。

**被否决**：① 退款记为收入——退货当月收入虚胖，一眼就看出来不对；② 直接改原单金额——原始事实被改写，导出与对账再也对不上；③ 拆成两笔无关联的账单——用户要自己维护父子关系；④ 允许多次退款超出原单——变成「我不知道退了多少」的黑洞；⑤ 部分报销（在原单上累计 `reimburse_amount_minor` 并加 `PART` 状态）——真实数据里已办结的报销全是整笔，为没有发生的场景多加一列、一个状态、一套「剔除未报销」的减法口径不划算。报销因此保持纯状态流：只改状态，不动金额。

## 31. 每月起始日：一处设置，四处生效

**问题**：发薪日不是 1 号的人，「本月支出」永远错位。但周期起点会同时影响首页、统计、预算、提醒。

**结论**：一个设置项（1–28），一个 `domain/Period.kt` 出口，四处引用。**提醒仍按自然日判定**，不参与周期起点。`ai_report.month_key` 跟着这个窗口走（见 §36），改起始日等于换一段区间重算一份。

**代价**：改动面大（首页分组、统计、预算、口径页四处都要重新走查）；「本月」标签在起始日非 1 号时要写成「10/15–11/14」。

**被否决**：① 只让预算用月起止日——首页与预算对不上更糟；② 允许 29–31——短月要定义「月末对齐」，多一条要解释的规则；③ 各页面自己算区间边界——`Period.kt` 是唯一出口，自己算就是违规。

## 32. 统计区间与搜索条件：先条件，后自然语言

**问题**：语义搜索（把一句话翻译成条件）和区间 / 条件补全是同一条落点的两个阶段。

**结论**：只做**条件层**：任意区间、二级小计、趋势、星期、金额区间、来源、排序、未列出条数。自然语言留作后续。

**代价**：搜索页顶部多一个「筛选」按钮，条件多了以后弹层变长（用分段 + 即时生效压住）。

**被否决**：① 直接上语义搜索——条件层没有落地就没有可生成的目标结构，模型只能猜；② 把条件塞进搜索框用 `金额>50 有图` 这类语法——自造查询语言，学习成本比点选更高；③ 排序不做——上限去掉后没有排序等于随机截断；④ 有无凭证 / 退款状态 / 报销状态 / 来源全枚举这几项筛选——按真实库判过：带凭证 1 笔、部分报销 0 笔、语音来源 0 笔，做出来是给想象出来的查询服务。

## 33. 批量跨账本迁移：只换账本，不搬分类

**问题**：批量原本不能改账本。原本以为难点是「目标本可能没有同名分类」加上周期 / 分期账单的幂等键会撞——但分类是**全机共用一套字典**，账本只管钱的归属、不参与分类树。于是迁移剩下的唯一真实约束是：**周期 / 分期生成的那些期次属于原计划**。

**结论**：弹层一步到位——列出未归档账本（源账本标「已在」，只有一个账本时整格置灰），点一行即提交，`UPDATE bill SET ledger_id = ?`。分类不动、不映射、不预检。带 `recurrence_rule_id` / `installment_plan_id` 的期次**整批跳过**，弹层与结果各说一句，让人在动手之前就知道有几笔不会跟着走。

**代价**：想把某一期的钱真正挪进另一个账本，得先回那个计划里停掉或改它——批量不动计划，这是有意的边界。

**被否决**：① 迁移时弹分类映射表——分类与账本无关，那一步没有任何对象可以映射，白白多两屏；② 把期次一并搬走，或自动改 `period_index` 避开索引——计划留在源账本，补记按 `(rule_id, index)` 判断那一月在不在，期被搬走等于计划里少一期，下一次补记把它再生成一遍，同一笔钱落进两个账本；改 `period_index` 更是直接动了自动化溯源；③ 搬之前先解绑规则——账单从此查不到自己的来源，周期卡的明细与「待补 N 笔」一起失真；④ 不做跨账本，让用户导出再导入——绕开所有校验，还会撞上判重。

## 34. 长图：直接画，不截屏；脱敏是一键

**问题**：想晒年报 / 给伴侣看，现在只能截屏拼图。技术上两条路：把 Compose 树渲染到屏外再截，或者用 `Canvas` 直接画。

**结论**：**`Canvas` 直接画**（宽度固定 1080px，高度按内容并有上限保险，IO 线程），数据复用统计四段与 AI 月报，预览用的就是出图那套渲染器。脱敏是**一个开关**：隐去所有金额与备注数字，保留分类、结构、比例与排序。**单笔明细与备注永不进图。**

**代价**：长图的排版要单独维护一套（不能直接复用 Compose 组件），换来的是可控尺寸与不依赖屏幕。

**被否决**：① 截屏方案——受设备密度与滚动限制，长内容会断；② 逐字段勾选脱敏——99% 的场景只有「全隐 / 全显」两种；③ 支持 PDF——多一个导出格式与分享路径，自用场景不需要；④ 长图里带 App 二维码 / 品牌页脚——这是自己的软件，不是产品推广；⑤ 逐段勾选要不要画——段落由维度定死，勾选组合会指数级增加要维护的版式。

## 35. 账本图标复用分类图标库

封面从 6 款渐变换成分类图标库 136 键，**复用分类选图标那套界面**（`IconLibraryPage` 加一档模式），不新做选择器。旧封面键按一次性映射换成语义相近的图标，渐变的 brush 与封面文件整体删除，不并存。

同时补 `icon_key` 入库校验：未收录键**拒绝写入**并内联给可选建议，不再静默退化成首字 tile——否则选了未收录的键又退化，等于白改。首字 tile 保留为**渲染兜底**（针对备份包带回的历史脏值），不再是写入路径的产物。

## 36. AI 报告的周期键：两端含当天的区间

**问题**：三种粒度原先各写各的——月 `2026-10`、年 `2026`、区间两个日期且右端写的是右开边界的后一天；摘要里给模型看的标签更短，`9/1–10/31` 连年份都没有，换一年查同一段，缓存和提示词都说不清是哪一年。

**结论**：`Period.key(range)` 一个出口，键一律写成两个 ISO 日期，**两端都含当天**、右端不越过今天：本月只过了 20 天就是 `2026-10-01_2026-10-20`，整月自然走到期末。落库的 `month_key`、摘要 JSON 与提示词里的「统计区间」共用这一串字。

**代价**：进行中的周期键每天挪一格，隔天打开弹层查不到「同一个月」的旧报告——多一次点击，数据没变时仍走 `input_sha256` 命中、不重复计费；改月起止日同样算换了一段区间，旧的「锚定月不变、缓存键不动」作废。

## 37. 不做什么（判断依据）

| 候选 | 判断 | 依据 |
|---|---|---|
| 账号 / 云同步 / 多端合并 | 不做 | 用户定的边界；服务端、冲突、成本、隐私四项同时到位才值得做 |
| 账户与资产、转账、借还、存钱计划 | 不做 | 都需要「余额」概念；`BillType.TRANSFER` 保持不可达 |
| 无障碍 / 通知监听记账 | 不做 | 常驻高权限 + 逐家 ROM 适配 + 误识别，与「用户主动触发」原则冲突 |
| 多币种 / 优惠券与手续费明细 | 不做 | 无场景；金额口径多一套「原价」概念的代价大于收益 |
| 收支日历 | 不做 | 按月分组 + 搜索（已支持区间与排序）足以定位「某天花了多少」，不为想象出来的动作再开一页；日历与首页功能重叠，还要回答「该进哪一页」 |
| 标签 | 不做 | 见 §9。归堆这件事账本已经承担得更好 |
| 部分报销 | 不做 | 见 §30 |
| 凭证多图 | 不做 | 见 §27 |
| 应用锁与生物识别 / PIN | 不做 | 见 §21 |
| AMOLED 纯黑第四档 | 不做 | 直接替换或新增一档都要重做一整套 token 与逐屏对比度校验；深色保持墨纸，黑位靠纸面本身控制 |
| 消息中心 / 通知历史 | 不做 | 见 §16 |
| 预算结转 / 按周预算 / 超支禁用保存 | 不做 | 见 §29 |
