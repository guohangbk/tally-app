## 1. 全局约定

| 约定 | 内容 |
|---|---|
| 主键 | 所有业务表用 `id TEXT`（UUID 字符串）；`app_setting` 用 `setting_key` 作主键 |
| 金额 | 一律 `*_minor INTEGER`，单位「分」，`Long`；业务层禁止浮点。方向由 `type` 表示，金额本身非负 |
| 时间 | 一律 `INTEGER` 毫秒时间戳（`System.currentTimeMillis()`），不做时区转换；日期归属按设备本地时区计算 |
| 布尔 | SQLite 无布尔列，用 `INTEGER` 0/1 |
| 软删除 | `deleted_at INTEGER NULL`；非空即已删除。所有查询默认带 `deleted_at IS NULL` |
| 同步预留 | `created_at` / `updated_at` / `deleted_at` / `device_id` / `version` 五列在除 `ai_config`、`app_setting` 外的所有表都存在；只写不读 |
| 外键 | 只有 `attachment.bill_id → bill.id`、`ai_message.conversation_id → ai_conversation.id`、`ai_message_attachment.message_id → ai_message.id` 声明了外键（`CASCADE`），其余引用关系靠应用层维护 |
| 列名 | 全部显式 `@ColumnInfo(name = "snake_case")`，不依赖 Room 命名策略 |
| 枚举 | 以字符串存枚举名（`type`、`status`、`source` 等），读回时用 `runCatching { valueOf() }` 兜底，脏值不崩界面 |
| **无迁移链，且不清库** | `version` 一直是 **1**，没有 `Migration(n, n+1)`、也不挂 `addMigrations`；改实体就直接改 `data/db/entity/` 的声明，手上那台设备的库按备份包重建。`fallbackToDestructiveMigration` 永不配——Room 的 identity hash 对不上时打开即抛异常停住，而不是把账清空 |
| **口径列不进索引热路径** | 退款冲抵、预算四个数字都以「应用层聚合 + 现有 `(ledger_id, occurred_at)` 索引」实现，不为口径单独造覆盖索引；只有查询确认真的变慢才加索引 |
| **偏好分两处** | 换机想带走的进 `app_setting`（随备份迁移）；属于这台设备的进 DataStore（不随备份）。API Key 与 WebDAV 口令永不进备份包 |

## 2. 表清单

| 分组 | 表 | 用途 |
|---|---|---|
| 主数据 | `ledger` | 账本 |
| 主数据 | `category` | 全机一套两级分类树 |
| 交易 | `bill` | 账单（唯一事实来源） |
| 交易 | `attachment` | 账单图片元数据 |
| 计划 | `budget` | 预算（总额与分类预算同一张表，`category_id` 为空即总额） |
| 迁移 | `import_batch` | 一次导入的对账与回滚记录 |
| 自动化 | `recurring_rule` | 周期记账规则与执行游标 |
| 自动化 | `installment_plan` | 分期计划（含房贷） |
| AI | `ai_config` | 服务商、模型、能力与连接状态 |
| AI | `ai_conversation` | 小莉会话 |
| AI | `ai_message` | 会话消息（含记账卡 DRAFT） |
| AI | `ai_message_attachment` | 会话内长期保留的图片 |
| AI | `ai_report` | 月度分析结果缓存 |
| 规则 | `keyword_rule` | 端侧关键词 → 分类 |
| 配置 | `app_setting` | 随备份迁移的键值偏好 |

共 **15 张表**。`import_source`（三种内置导入来源与列映射）已删除——整表与 `ImportDao` 无调用方，三种来源继续内置在 `ImportParsers`。

给「导出诊断包」用的 `DiagnosticDao` 只做计数与 AI 健康度查询，**不是一张表**：`@Query` 不走 entities，identity hash 与 `version` 都不动（见 §5.5）。

## 3. 逐表字段

### 3.1 `ledger` 账本

| 列 | 类型 | 非空 | 含义 |
|---|---|---|---|
| `id` | TEXT | ✓ | 主键 |
| `name` | TEXT | ✓ | 账本名 |
| `icon_key` | TEXT | ✓ | 封面图标键，值域是分类图标库（136 键），默认 `coin` |
| `is_default` | INTEGER | ✓ | 全局唯一默认账本标记 |
| `is_archived` | INTEGER | ✓ | 归档；归档后不出现在切换列表 |
| `sort_order` | REAL | ✓ | 列表顺序 |
| 通用列 | — | — | — |

索引：`is_default`、`deleted_at`。约束：默认账本不能归档也不能直接删除，由 `LedgerRepository` 保证。

### 3.2 `category` 分类

| 列 | 类型 | 非空 | 含义 |
|---|---|---|---|
| `id` | TEXT | ✓ | 主键 |
| `parent_id` | TEXT | | 为空即一级；非空指向同收支类型的一级 |
| `name` | TEXT | ✓ | 分类名 |
| `type` | TEXT | ✓ | `EXPENSE` / `INCOME` |
| `icon_key` | TEXT | ✓ | 图标键，二级各自独立不继承一级 |
| `color` | TEXT | | 预留色 |
| `sort_order` | REAL | ✓ | 拖拽后取相邻中点 |
| `is_system` | INTEGER | ✓ | 系统预置分类，只能归档不能删 |
| `is_archived` | INTEGER | ✓ | 归档；归档后不出现在记账页选择器 |
| 通用列 | — | — | — |

索引：`parent_id`、`(type, sort_order)`。**全机一套**：本表没有 `ledger_id`，也不存在账本-分类关联表；任何账本共用同一棵两级树。

`is_archived` 只表示**自身**归档，子树是否可见由查询侧按父级状态判定（`CategoryDao` 的 active-only 查询收口）。

### 3.3 `bill` 账单

| 列 | 类型 | 非空 | 含义 |
|---|---|---|---|
| `id` | TEXT | ✓ | 主键 |
| `ledger_id` | TEXT | ✓ | 所属账本 |
| `category_l1_id` / `category_l2_id` | TEXT | | 两级分类，可空（未分类） |
| `type` | TEXT | ✓ | `EXPENSE` / `INCOME`（`TRANSFER` 仅枚举预留，全仓无构造点） |
| `amount_minor` | INTEGER | ✓ | 金额（分），非负 |
| `currency` | TEXT | ✓ | 固定 `CNY` |
| `occurred_at` | INTEGER | ✓ | 发生时间 |
| `time_precision` | TEXT | ✓ | `DATE` / `DATETIME`，决定分组粒度 |
| `note` | TEXT | | 备注 |
| `source` | TEXT | ✓ | `MANUAL` / `VOICE` / `SCREENSHOT` / `RECURRING` / `INSTALLMENT` / `IMPORT` |
| `external_id` | TEXT | | 导入原始 ID，用于去重 |
| `fingerprint` | TEXT | | 组合指纹，无 `external_id` 时去重用 |
| `reimbursed` | TEXT | ✓ | `NONE` / `PENDING` / `DONE` |
| `reimbursed_at` | INTEGER | | 报销日期，撤销报销后仍保留供回查 |
| `refund_of_bill_id` | TEXT | | 指向被退款的原单 `bill.id`；非空即退款笔 |
| `is_refund` | INTEGER | ✓ | 退款标记（导入映射用） |
| `is_reimbursement` | INTEGER | ✓ | 该笔本身就是一条报销记录 |
| `excluded_from_stats` | INTEGER | ✓ | 不计入收支 |
| `recorder` | TEXT | | 记账人（导入映射） |
| `linked_external_id` | TEXT | | 关联账单原始 ID，只服务导入 |
| `recurrence_rule_id` / `installment_plan_id` / `period_index` | | | 自动化溯源与幂等键 |
| 通用列 | — | — | — |

索引：`external_id` UNIQUE、`fingerprint`、`(ledger_id, occurred_at)`、`(category_l1_id, category_l2_id)`、`deleted_at`、`refund_of_bill_id`、`(recurrence_rule_id, period_index)` UNIQUE、`(installment_plan_id, period_index)` UNIQUE。

统计口径：**所有汇总查询统一 `deleted_at IS NULL AND excluded_from_stats = 0`**，支出合计再排除 `reimbursed = 'DONE'`——已报销的钱会回来，不占这一期的支出，那几笔另记在 `BillSummary.reimbursedMinor / reimbursedCount` 里对账。待报销（`PENDING`）照常计入；统计页那个「不计待报销」开关是另一层可选剔除，与这一条不冲突。

退款行保持 `type = 'EXPENSE'` 并写 `is_refund = 1`；`refund_of_bill_id` 非空时按原单分类冲抵（见 §7）。

### 3.4 `attachment` 账单图片

| 列 | 类型 | 非空 | 含义 |
|---|---|---|---|
| `id` | TEXT | ✓ | 主键 |
| `bill_id` | TEXT | ✓ | 外键 → `bill.id`，`CASCADE` |
| `relative_path` | TEXT | ✓ | 相对 `files/attachments/` 的路径 |
| `sha256` | TEXT | ✓ | 内容哈希，用于去重与备份校验 |
| `mime_type` / `size_bytes` / `width` / `height` | | ✓ | 元数据（WebP） |
| 通用列 | — | — | — |

索引：`bill_id`、`sha256`、`deleted_at`。**一笔一张凭证**（多图与逐张管理砍掉，`sort_order` 列从未加过）。文件删除是软删行，物理文件按 `sha256` 引用计数回收：同一文件可被多笔共享，只有零引用且超保留期才删。

### 3.5 `budget` 预算

| 列 | 类型 | 非空 | 含义 |
|---|---|---|---|
| `id` | TEXT | ✓ | 主键 |
| `ledger_id` | TEXT | ✓ | 预算按账本，各本独立 |
| `category_id` | TEXT | | 为空即**总额预算**；非空必须是一级分类 id |
| `period` | TEXT | ✓ | `MONTHLY` / `YEARLY` |
| `amount_minor` | INTEGER | ✓ | 预算额（分），非负 |
| `alert_ratio` | INTEGER | ✓ | 提醒阈值，百分数，默认 `80`；`100` 即只在超支时提醒 |
| `is_active` | INTEGER | ✓ | 停用而不删除；停用后不参与提醒与进度 |
| `period_start` | INTEGER | ✓ | 这一条属于哪个周期段（起点毫秒）；不匹配任何真实月份的行不参与任何页面 |
| `auto_renew` | INTEGER | ✓ | 下一段要不要自动复制 |
| 通用列 | — | — | — |

索引：`(ledger_id, period)`、`category_id`。**不设唯一索引** `(ledger_id, period, category_id)`：软删行仍占唯一位，恢复时会撞；重复由 `BudgetRepository` 写入前校验。

周期边界不存日期，由 `domain/Period.kt` 按 `month_start_day` 现算——存日期会导致改了月起止日后旧预算对不上。

### 3.6 `import_batch`

`source_type`、`ledger_id`、`file_name`、`source_sha256`、`total_rows` / `imported_rows` / `skipped_rows` / `failed_rows`、`report_json`（对账明细）、`status`、`started_at` / `finished_at`。索引 `ledger_id`、`status`、`source_sha256`。

### 3.7 `recurring_rule` 周期规则

| 列 | 含义 |
|---|---|
| `ledger_id`、`name`、`type`、`amount_minor`、`category_l1_id/l2_id`、`note` | 生成账单的模板字段 |
| `frequency` | `DAILY` / `WEEKLY` / `MONTHLY` / `YEARLY`（含月末规则） |
| `day_of_month` / `day_of_week` / `month_of_year` | 按频率取用其一 |
| `start_at` / `end_at` / `max_periods` | 结束条件：永不结束 / 到日期 / 满 N 期 |
| `last_executed_at` / `next_due_at` / `executed_periods` | 执行游标 |
| `last_reminded_at` | 到期通知游标，同日只发一条 |
| `status` | `ACTIVE` / `PAUSED` / `FINISHED` |

索引：`ledger_id`、`status`。幂等：生成时写 `bill.recurrence_rule_id + period_index`，唯一索引兜底。

### 3.8 `installment_plan` 分期计划

`principal_minor`（本金）、`fee_minor`（手续费）、`fee_mode`（`NONE` / `PER_PERIOD` 并入每期 / `EXTRA_PERIOD` 单独成期）、`total_minor`、`period_count`、`per_period_minor`、`tail_minor`（末期尾差）、分类与 `first_occurred_at`、`interval_months`、`generated_periods`、`status`、`note`、`last_reminded_at`、`repayment_method`（`PLAIN` / `EQUAL_PAYMENT` 等额本息 / `EQUAL_PRINCIPAL` 等额本金）、`annual_rate_bp`（首期年利率，万分之一）、`rate_changes_json`（固定利率下调息记录 `[{"from":n,"bp":x}]`，`from` 从 1 起；改利率从 `generated_periods + 1` 追加，NULL 表示从未变过）。索引 `ledger_id`、`status`。

合计校验：`per_period × (n − 1) + (per_period + tail) = total`。

### 3.9 AI 五表

| 表 | 关键列 | 说明 |
|---|---|---|
| `ai_config` | `provider`、`base_url`、`model`、`key_reference`、`status`、`vision_capable`、`last_error`、`consecutive_failures`、`updated_at` | 单行表（`id = "default"`）。`provider` 存预置键，`openai_compatible` 表示自定义；`key_reference` 只是 Keystore 条目名，明文不落库；`vision_capable` 由用户在配置页勾选 |
| `ai_conversation` | `title`、`context_summary`、`archived_at` | 摘要为本机折叠文本，不由模型生成 |
| `ai_message` | `role`、`content`、`message_type`、`status`、`sequence`、`error_code`、`duration_ms` | `message_type` 含 `DRAFT`：记账卡以消息形态落库，进程回收后卡片与「已记入」状态仍在 |
| `ai_message_attachment` | `message_id`、`relative_path`、`sha256` | 只存需要长期保留的图；发送中的临时图不入库 |
| `ai_report` | `ledger_id`、`month_key`、`input_sha256`、`summary_json`、`content` | `(ledger_id, month_key)` 查这一段，`month_key` 是两端含当天的区间（`2026-10-01_2026-10-20`）；`input_sha256` UNIQUE 保证同一份输入不重复生成 |

### 3.10 `keyword_rule` 与 `app_setting`

`keyword_rule`：`keyword`、`category_id`、`priority`、`source`（`BUILTIN` 内置只读 / `MANUAL` 用户加 / `LEARNED` 记账页沉淀）。索引 `keyword`、`category_id`。**全机一套**——没有 `ledger_id`。内置词组不落这张表（仍在 `QuickNoteRules` 里，按分类 **id** 绑定）。

`app_setting`：`setting_key` 主键 + `setting_value` + `updated_at`。随包迁移的键只有四个：`default_currency`（`CNY`）、`month_start_day`、`recycle_keep_days`、`recycle_last_cleanup`。通知开关、每日时刻、锁屏是否带金额、预算阈值与各类游标都存 DataStore——**那是这台设备上的打扰意愿**，换机与恢复备份不该把「我在这台机器上不想被打扰」带过去。只有需要随备份迁移的偏好才放这张表。

## 5. 版本与迁移策略

### 5.1 现状

`version = 1`，`exportSchema = true`，KSP 每次构建把当前版本的 `schemas/…/1.json` 导出到 `tally-app/schemas/`（编译期产物，不入库）。**没有迁移路径**：改实体直接改 `data/db/entity/` 的声明，`version` 不动，`di/AppGraph.kt` 也不挂 `addMigrations`。本目录的 `db/1.json` 是发版时冻结的那份快照，与 `tally-app/schemas/…/1.json` 逐字节一致（本次刷新后核对：SHA-256 `006EB08A0BD73966CCC9B73906857562338C7C4F579D17A15E4F4CB0DA3BCEB4`）。

| 版本 | 改了什么 |
|---|---|
| 1 | 15 张业务表建齐 + `ai_config` 加 `active` 列（多条配置里哪一条正在生效）。此后改实体都不抬版本号 |

**为什么可以不走迁移**：手上那台设备的库每次都是按备份包重建的，不存在「从旧版升上来」的路径要照顾；凭空保留一串升不上来的迁移只是没人能验证的死码。

**但有一条硬约束**：Room 每次打开库都会拿编译期算出的 identity hash 与库里 `room_master_table` 存的值比对，**版本号相同而 hash 不同就直接抛 `IllegalStateException: Room cannot verify the data integrity`**，崩在进程里（不是降级、不是忽略）。所以每次改了实体，已经装在设备上的库都必须重建——备份包导入，或覆盖安装前先清库。

### 5.2 改实体的规矩

| 约定 | 理由 |
|---|---|
| 改实体就改 `data/db/entity/` 的声明，`version` 保持 1，不写迁移段 | 手上没有需要升上来的旧版本 |
| **永远不配** `fallbackToDestructiveMigration` | 缺校验时打开会抛异常并停在可恢复提示。留着它等于开一条静默清库的后路——崩了数据还在能修，清了就没有了 |
| 每次实体改动重跑 KSP 导出 `1.json`，并把 DDL 与本文档对一遍 | 导出 JSON 是本机上唯一能逐字段对照的东西 |
| 改完实体，手上设备的库按备份包重建，并核对首页总额 | Room 的 identity hash 校验会挡住旧库，见 §5.1 |
| 不为无实体变化的版本空转号 | 没改表就不 +1 |

### 5.3 自测（无自动化测试的前提下怎么验）

1. 装当前包，造一批数据（含关键词规则、账本封面、归档分类、带图账单）。
2. 导出 `.tally` 备份与 CSV 作为基线。
3. 改实体后重新构建，**先清库再装**（卸载重装，或从备份包导入）——旧库里的 identity hash 对不上，覆盖安装会直接崩，见 §5.1。
4. 核对首页总额、分类数与第 2 步一致。
5. 故意把库里 `room_master_table` 的 identity hash 改脏再装，确认是报错停住而不是清库。

### 5.4 升级路径

| 从 | 到 | 路径 |
|---|---|---|
| 本库（version 1） | 任意后续版本 | 无迁移路径：改实体直接改声明，设备上的库按备份包重建 |
| 高于当前 App 的库 | — | 拒绝启动并提示先升级 App（备份包按 `manifest.dbVersion` 同规则） |
| 任何版本 | — | 不存在清表重建路径（`fallbackToDestructiveMigration` 永不配） |

### 5.5 只读 DAO：`DiagnosticDao`

「导出诊断包」需要一个只做计数与状态查询的 DAO，落点 `data/db/dao/DiagnosticDao.kt`。**它不改变这张表清单，也不改任何表结构**：

- `tableRows()` 一条 `UNION ALL` 出 **17 项行数**：`bill` / `bill_live` / `ledger` / `ledger_live` / `category` / `budget` / `attachment` / `import_batch` / `recurring_rule` / `installment_plan` / `ai_config` / `ai_conversation` / `ai_message` / `ai_message_attachment` / `ai_report` / `keyword_rule` / `app_setting`（带 `_live` 的两项再滤一次 `deleted_at IS NULL`）。
- `aiHealth()` 只取 `provider / model / last_error / consecutive_failures`：**`base_url` 与 `key_reference` 不进诊断包**；`last_error` 存的是失败类型名而不是响应正文，所以不会带进对话内容。
- 加 DAO 不改表结构：Room 的 identity hash 只由 `entities` 决定，所以**不抬版本、不需要迁移**。`PRAGMA user_version` 与 `room_master_table` 也不在这个 DAO 里查——Room 解析不了 `PRAGMA`，那张表要到运行时才存在，只能走裸连接（`Diagnostics.rawFirst`）。

## 6. 索引与查询

| 查询 | 做法 |
|---|---|
| 首页按日分组 | 一次区间查询取行，按本地日期在应用层归堆（SQLite 的日期函数按 UTC，跨时区会错一天） |
| 任意起止区间统计 | 现有区间查询的两个边界参数即可，无需新 SQL；区间由 `domain/Period.kt` 算 |
| 列表排序 | `ORDER BY` 由写死改为受控枚举（时间正/倒、金额大/小），四种都走 `(ledger_id, occurred_at)` 或 `amount_minor` 索引 |
| 搜索结果上限 | 1000 笔，保留 `truncated` 标志并在界面显示「还有 N 条未列出」，不静默截断 |
| 退款冲抵 | 不在主区间查询里 join 原单：只在区间内出现退款行时，按 id 补一次原单查询拿分类，避免给热路径加连接 |
| 回收站列表 | 复用 `bill(deleted_at)`；按 `deleted_at DESC` 排序与「超保留期」清理查询 |
| 预算进度 | 聚合复用区间查询结果，在应用层按 `budget.category_id` 归堆；不新增 SQL 聚合 |
| 导出 | 13 列 = `ID` + 12 列模板字段（时间 / 账本 / 分类 / 二级分类 / 类型 / 金额 / 币种 / 备注 / 已报销 / 记账者 / 账单图片 / 关联账单）；无标签列 |

## 7. 统计口径（全站唯一定义）

| 口径 | 定义 | 影响面 |
|---|---|---|
| 基础口径 | `deleted_at IS NULL AND excluded_from_stats = 0` | 全部汇总 |
| **退款冲抵** | `refund_of_bill_id` 非空且 `is_refund = 1` 的行，**在退款自己所属的周期与账本里**从**原单所属分类**的支出中扣减，不计收入；原单分类为空时扣到「未分类」。原单被删或从未关联的退款是中性行，不进任何合计 | 首页汇总条、统计四段、搜索合计、导出合计、预算进度 |
| **月起止日** | `month_start_day`（1–28，默认 1）决定「本月」的 `[startAt, endAtExclusive)`；`ai_report.month_key` 跟着这个窗口走，改起始日等于换一段区间重算一份 | 首页分组、统计、预算、每日提醒判定 |
| **预算** | 预算比较的是**冲抵后的净支出**，与统计页看到的数字一致；`excluded_from_stats = 1` 的笔不占预算 | 预算页、通知、首页进度 |

`domain/Period.kt` 是月起止日的唯一出口：`monthRange(anchor, startDay)` / `yearRange(anchor, startMonth)`。任何页面自己算边界都算违规。

## 8. 事务边界

| 操作 | 同一事务内的写入 |
|---|---|
| 新增 / 编辑 / 删除账单 | 账单行、分类校验、附件元数据变更 |
| 批量操作 | 逐条写入但整体提交；失败逐条报因，不回滚已成功项 |
| 导入 | 解析结果落库、去重、关联解析、`import_batch` 对账结果；对账不平整批回滚 |
| 周期 / 分期补执行 | 每个批次先查幂等键再写入，单事务提交 |
| 退款保存 | 退款行 + 原单累计校验（同一原单并发退款靠事务内重读兜底） |
| 预算保存 | 预算行 + 阈值校验，不触发账单写入 |
| 跨账本批量迁移 | 一条 `UPDATE bill SET ledger_id = ? WHERE id IN (:ids)`，与 `updated_at / version` 同写。**分类不参与**——全机共用一套字典。带 `recurrence_rule_id` / `installment_plan_id` 的期次由界面层整批跳过（计划留在源账本，期搬走会被补记再生成一遍） |
| 回收站恢复 | 账单行 `deleted_at` 置空 + `attachment` 同步复位 |
| 彻底删除 | 账单行物理删 + 附件引用计数更新（物理文件回收在清理任务里做，不在删除事务里做 IO） |
| 附件清理任务 | 按 `sha256` 引用计数判定：同一文件可被多笔共享，**只有零引用且超保留期才物理删**；先删文件后软删行，失败可重跑 |
| 恢复备份 | 临时库导入并校验 → 通过后单事务覆盖当前库 |
| 生成备份 | 只读快照，不加写锁 |

## 9. 查询与写入约束（实现层必须守住）

1. 统计口径统一：`deleted_at IS NULL AND excluded_from_stats = 0`；「不计入收支」单独可查但不进合计。
2. `category_l2_id` 非空时其父级必须等于 `category_l1_id`，写入前在 Repository 校验。
3. 周期与分期生成必须走幂等键，唯一索引是最后一道防线。
4. 删除分类前必须先迁移其账单引用，迁移目标要求同收支类型、同层级、未归档、非自身。
5. 列表查询按 `(ledger_id, occurred_at)` 走索引；分类树一次取全量在内存组树，避免 N+1。
6. 预算的 `category_id` 非空时必须是一级分类；同 scope 的重复由 Repository 写入前校验，不靠数据库唯一索引。

## 10. 备份包与本库的映射

| 项 | 内容 |
|---|---|
| 容器 | ZIP：`manifest.json`（明文）+ `data.enc` + `attachments/<sha256>` |
| 加密 | AES-256-GCM，密钥由口令 PBKDF2 派生 120,000 轮 |
| 覆盖表 | 全部 15 张表 |
| `manifest.json` | 带 `dbVersion` 字段：包内版本高于当前 App 时明确拒绝并提示先升级 |
| 口令 | 下限 4 位、允许字母；只提下限，旧包仍可正常恢复 |
| 剔除字段 | `ai_config.key_reference`（恢复后按未配置显示） |
| 不在包内 | API Key、WebDAV 口令、DataStore 偏好；图片仅在勾选「包含图片」时打包 |
| 恢复方式 | 校验口令与哈希 → 临时库导入校验 → 单事务覆盖替换 |
| 恢复后必做 | 重新配置小莉 Key 并重测；通知授权需重新申请；未打包图片显示「图片未包含在备份中」 |

登记点四处必须同步，漏一处即恢复后静默丢数据：`data/backup/BackupJson.kt` 的 `BackupSnapshot` 与 encode / decode、`BackupService.kt` 的 `loadSnapshot` / restore 插入 / `clearAll`、`TallyDatabase.kt` 的 entities。
